# Selfie enrollment integration

## Implemented synthetic staging issuance

**Issue selfie credential** appears only in the initialized developer menu, below
faux issuance. It prepares schema 11 in the existing browser WalletKit, calls the
localhost-only `/api/selfie-credential` route, polls staging, verifies the returned
credential's signature against the current staging schema registry and its subject,
and stores it with the browser-held blinding factor. An active schema-11 credential
prevents another issuance. Deleting the credential does not delete its enrollment;
clicking issue again retrieves the existing result, rather than refreshing it.

The local `src/server/face-enrollment-helper` helper uses pinned AMPC sharing/sealed boxes,
Oxide enrollment authentication, and credential verification primitives. Build with
`npm run build:selfie-helper` (Cargo must be on PATH; private GitHub dependency
access is required). The direct Oxide dependency also requires `wget`, `jq`,
`protoc` (protobuf), and the native C/C++ toolchain for its transitive biometric
dependencies. `build-config.toml` supplies Oxide's upstream asset-download settings.

Authentication uses pinned Oxide `329274a32be02be0bb39ca02adc4e4e4e438ada0`
`ZkpAuthentication::create_header` with API v1. Oxide fetches the challenge and
builds the proof/header. The saved seed remains UTF-8 hexadecimal text with
`IdentityContext::Orb` (`identity_trapdoor`), preserving existing enrollment
identities; switching to Face context would change them. The helper now makes
staging authentication requests and is bounded by its parent process deadline.
It does not invoke WalletKit CLI or receive the wallet seed,
passkey PRF outputs, database key, or blinding factor. Synthetic input is generated
using `FaceVector::random_normalized`; the preview fixture below is separate.

Only the staging enrollment endpoint is enabled. Like Orb Tools, this fixture uses
`staging-test-token` headers, a synthetic associated-data hash, and omits attested
share hashes. It has no actual camera capture, liveness check, or recoverable PCP.

A private operation file under
`~/.local/state/web-authenticator/synthetic-selfie-issuance` contains a separate
staging enrollment identity seed, capture ID, token hash, and submission state
(directory 0700, files 0600). An opaque resume token is saved in browser localStorage;
it is not a wallet secret. Neither signed credentials nor embeddings are saved on
the server. An ambiguous submission is only polled, never resubmitted automatically.
If the backend never accepted it, it remains unresolved and requires investigation.
The original decimal-commitment request format was rejected with HTTP 400 before
enrollment storage. That specific saved rejection can retry once, on the next
button click, after migrating to the required padded-hex format; it retains the
same seed and capture ID. Other rejected or ambiguous attempts are not reset.
No automatic refresh or deletion of backend enrollment is implemented.

The WalletKit worker attaches only schema 11's first stored claim (the score),
matching the iOS disclosure policy. This makes IDKit 4.3.0 able to decode the selfie
response. The demo RP verifies the credential proof against the staging contract;
it does **not** authenticate the separately disclosed score, App Attest integrity,
or user presence. Requests requiring user presence remain blocked by the drawer.

## Development fixtures and enrollment boundary

The synthetic-result preview and its capture fixture are kept in the ignored
local `demo/fixtures/` directory. They are not imported or rendered by the
authenticator. The staging issuance flow described above still uses synthetic
input generated by the native helper.

`src/lib/staging-face-enrollment.ts` copies Orb Tools' enrollment exception into a
request builder restricted to `https://app.stage.face.worldcoin.org/api/v1/identity`.
It supplies both staging integrity headers and retains the required `x-zkp-proof`.
It bounds the payload and request deadline and rejects redirects. The issuance route now constructs its multipart request directly with FormData;
this earlier request-builder helper remains unused. No enrollment has been
submitted automatically.
This exception is scoped to signup admission; RP verification is a separate service.

`spoofScore` is a PAD result, not the issuer's sybil score. Neither belongs in logs.
Latest reviewed iOS reads the selfie credential's first stored claim and attaches
that claim to its proof response. It does not hardcode `sybil_score: 10`.
It then computes a digest including the claims and obtains an integrity bundle.

## Planned TEE enrollment and native-compatible PCP custody

The [upstream/WASM plan](wasm-upstream-plan.md) fixes share generation in the TEE.
The steps below describe the target implementation; current staging issuance
remains synthetic. Exact custody output and PCP assembly boundaries must be
specified with the service owners while preserving the canonical package format.

1. Reuse the initialized WalletKit session and `prepareCredential(11n)`; retain the
   subject and blinding factor for this operation. Do not register a new identity.
2. Obtain the accepted embedding and its exact custody data through TEE-backed
   enrollment. The TEE quantizes the embedding, generates AMPC shares, encrypts
   them to authenticated party keys and attests the bound output. Implement a
   small PCP-only WASM surface from existing Oxide hashing, package and custody
   crypto code as needed; exclude quantization, share generation and party
   encryption. The installed `walletkit-web@0.22.1` does not expose these custody
   APIs. Confirm dependency compatibility before choosing the binding revision;
   do not bundle native camera/model inference into the browser.
3. Build Face PCP v1 associated data: identity commitment, capture ID/time, original
   embedding plus metadata, accepted PNG, and three AMPC shares of the quantized
   embedding. Resolve the enrollment identity explicitly: iOS supplies a face
   identity separately from the v4 credential subject; an authenticator address is
   not a substitute for that commitment.
   Use the TEE-produced shares for custody and enrollment; never independently
   generate a second set. Deliver sensitive custody data encrypted to the user's
   authenticated custody key rather than exposing it to the relay or issuer.
4. Package with the enrollment attestation material. iOS uses the same integrity
   session in the package and enrollment request. The web flow requires a defined
   TEE evidence contract accepted by the issuer; it cannot label that evidence as
   iOS App Attest. A synthetic fixture cannot supply
   that material. For staging, use the copied Orb Tools test-admission headers;
   they are not genuine attestation material to put into a production PCP. Keep
   synthetic packages explicitly identified as test artifacts.
5. Encrypt and read back the pending package before submission, preserving the
   operation ID, subject, and blinding factor in encrypted recovery state. Derive a
   versioned PCP custody key from our storage secret during unlock, before clearing
   raw secrets. For native-format interoperability use Oxide's personal-custody
   public-key sealing, not an AES envelope described as native-compatible. Store
   ciphertext in IndexedDB separately from WalletKit's OPFS credential store.
6. Submit the encrypted AMPC shares and hashes bound to that package and subject;
   use bounded polling. Reconcile interrupted/unknown submissions under the same
   operation instead of automatically creating another enrollment.
7. Validate the returned issuer credential and subject binding, call
   `storeCredential(bytes, blindingFactor)`, insert `credential.json` into the PCP,
   and save the updated encrypted package. Recover interrupted local commits from
   the same persisted issuer result. Track local completion and cloud backup
   separately; syncing a passkey does not sync PCP ciphertext.
8. Expose the required stored credential claims through WalletKit's worker API.
   Attach the actual z-score claim when building selfie responses and bind it into
   the integrity flow. Keep IDKit 4.3.0 and request `selfie`.

The PCP archive contains optional `credential.json`, `associated_data/info.json`,
`associated_data/face_embeddings.json`, `associated_data/face_image.png`, three
`associated_data/face_ampc_share_{0,1,2}.json` files, and
`signed_hashes_attestation_gw.sign`. A saved embedding alone is not this package.

## Developer storage controls

The credential vault provides per-credential deletion and deletion of all displayed
local credentials, with explicit confirmation. The WalletKit package patch exposes
`CredentialStore.deleteCredential` through its existing worker. Deletion preserves
registration and the passkey; it does not call issuer-side revocation/deletion.
Failures report confirmed deletions and refresh the list, including partial batches.

The separate **Delete local PCP** control is disabled while PCP persistence is not
implemented. It must later target only this authenticator's local PCP records, not
clear origin storage or delete cloud backups. This follows iOS's separate local-PCP
reset action; iOS's face-credential deletion has broader backend effects that this
web developer control intentionally does not invoke.
